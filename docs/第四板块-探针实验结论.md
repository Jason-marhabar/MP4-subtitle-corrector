# 第四板块（ASR 识别 + 字幕校正）Aboboo 对齐探针实验结论

> 实验日期：2026-10-09  
> 素材：`test.mp4`（720×1280，H.264+AAC，44.1kHz 立体声，313.12 秒，英语跟读素材）  
> 执行人：第四板块负责人  
> 一句话结论：**Aboboo 对齐完全由 SRT 时间戳决定，与 MP4 无关；Whisper 时间戳系统性偏早，必须用"波形吸附"校正。**

## 一、核心认知：对齐的因果链（已用硬证据确认）

Aboboo 官方文档明确：**"字幕时间戳用作断点"**、**"原文字幕和译文字幕的时间戳必须相近，最好相同，否则后加载的字幕会覆盖之前加载的字幕"**
（依据：[Aboboo 看电影学外语](https://aboboo-docs.readthedocs.io/en/latest/ref/movie/overview.html)）

由此推出三条铁律，直接决定各板块的职责边界：

| 铁律 | 证据 | 对分工的影响 |
|---|---|---|
| **对齐 = SRT 时间戳的绝对精度** | Aboboo 用时间戳切分音频断点 | 全部压力在**第四板块** |
| **MP4 只需时间轴不变，无需"矫正"** | 实测 `-c copy` 逐帧偏差 **0.000000ms** | 第三板块的 `-c copy` 是正确做法，**不要重编码** |
| **音频标准化对对齐零帮助** | Aboboo 首次打开会自行提取音轨、采样、生成断点 | 标准化只增加 Aboboo 的解析负担，降级为可选 |

**结论：交付物应定义为「1 个 remux mp4 + 1 个校正后 srt」。"矫正后的 mp4" 本质只是规范化封装，不含任何时间轴改动。**

## 三、实验结果

### 3.1 Whisper 时间戳系统性偏差（核心发现）

方法：用 ffmpeg `silencedetect` 从**音频波形**提取真实语音起点（独立于任何 ASR 的客观参照），再让 Whisper 词级转写，统计"每段首词起点 − 最近真实语音起点"。

> ⚠️ **方法学教训**：第一版实现把所有词都拿去就近匹配语音起点，导致**句中词被误配**，算出"+174ms 偏晚"的错误结论。修正为**只用每段首词**后结论完全反转。**做这类测量必须只用段首词，并且每个锚点只接受一个最佳配对。**

| 模型 | 中位数偏差 | 偏早比例 | 标准差 | 配对成功 |
|---|---|---|---|---|
| small (int8, CPU) | **−92ms** | 85.4% | 133ms | 41/54 |
| large-v3 (int8, CPU) | **−267ms** | 88.5% | 156ms | 26/63 |

**结论**：
- Whisper 时间戳**系统性偏早**，两个模型同向，幅度随模型增大而增大（−92ms → −267ms）。
- 标准差 130~160ms 且逐句不一致 → **单纯做全局补偿无法解决**，必须逐句吸附。
- 对 Aboboo 而言"提前"比"滞后"安全（复读时字幕已就位、声音尚未到），但 −267ms 已接近一个音节，仍需校正。
- 偏早量是**素材与模型相关**的，不能写死。生产环境应把"吸附"作为标准步骤，而不是补偿固定毫秒数。

### 3.2 波形吸附算法（已验证有效）

算法关键点：**吸附到「>= 该起点的下一个语音起点」，而不是「最近的」语音起点。**

实测逐条证据（前 10 段，Whisper 起点几乎都落在静音里，且都比真实起点早）：

| 序 | Whisper 起点 | 真实语音起点 | 提前量 | 文本 |
|---|---|---|---|---|
| 1 | 0.000s | 0.378s | 378ms | Unit 1. Clubs in our school. |
| 2 | 3.160s | 3.289s | 129ms | Topic words. |
| 3 | 6.940s | 7.085s | 145ms | Gardening. Gardening. |
| 4 | 11.720s | 11.698s | −22ms（在语音内） | Photography. Photography. |
| 5 | 16.720s | 16.772s | 52ms | Art. Art. |
| 6 | 20.880s | 20.939s | 59ms | Storytelling. Storytelling. |
| 7 | 26.120s | 26.195s | 75ms | Pottery. Pottery. |

**若改用"最近的语音起点"**，当段起点落在静音中时会被吸到**上一句**开头，把字幕整体推前一整句 —— 实测该错误做法产生 **2403ms 的中位修正量**，完全不可用。

**吸附效果（small 模型，54 条字幕，123 个有效锚点）**：

| 指标 | 结果 |
|---|---|
| 起点成功吸附 | 49 / 54 |
| 起点修正量中位数 | **145ms**（与独立测得的 −92ms 方向一致、量级吻合） |
| 吸附后残差中位数 | **0ms** |
| 精确命中语音起点 | **49 / 54 条** |
| 残差平均 | 58ms |
| 自检（重叠/逆序/过短） | ✅ 全部通过，**零重叠** |

### 3.3 REMUX 完整性（第三板块验证）

对 `test.mp4` 与 `-c copy` 输出做**逐帧 PTS 比对**：

```
比对帧数: 2702
最大偏差: 0.000000 ms
完全一致的帧: 2702/2702
```

且两条输出的音频/视频 `start_time` 均为 `0.000000`。

**结论：`-c copy` 封装对时间轴零影响，"音画偏移"风险在本素材上不存在。** 顺带修复了原 `ffmpeg_processor.py` 的一个缺陷：`audio_normalize=True` 时 `loudnorm` 会把音频重采样到 96kHz（原 44100Hz），必须显式加 `-ar 44100`。

### 3.4 SRT 结构规则（双工具交叉验证）

用 8 个精心设计的变体做对照实验，**自研校验器与 `seconv lint` 结论完全一致**：

| 变体 | 自研校验器 | seconv lint |
|---|---|---|
| A 基准 UTF-8 | ✅ 干净 | ✅ clean |
| B 带 BOM | ⚠️ 警告 BOM | ✅ clean（**未检查 BOM**） |
| C GBK 编码 | ❌ 编码非 UTF-8 | ✅ clean（**未检查编码**） |
| D 重叠 + `end<start` | ❌ 重叠 300ms + 负时长 | ⚠️ overlap 300ms + negative-duration −500ms |
| E 整体提前 500ms | ✅ 干净（结构上合法） | ✅ clean |
| F 零间隙 | ⚠️ 5 处间隙为 0 | ⚠️ gap-too-short 0ms（min 24ms）×5 |
| G 超长行 154 字符 | ⚠️ 超长 + 阅读过快 | ⚠️ line-too-long 154（max 43） |
| H 空文本/零时长 | ❌ 空文本×2 + 零时长 | ⚠️ empty×2 + zero-duration |

**seconv 的默认阈值（实测得来）**：行长上限 **43** 字符、最小间隙 **24ms**、单条最长显示 **8000ms**、最短显示 **1000ms**。

**⚠️ 重要发现：`seconv info` 的 BOM 检测不可信。**
对 4 个文件做字节级核对（前 3 字节）：

```
test_A_utf8.srt      31 0A 30 ...  无 BOM   ← seconv 却报 "utf-8 (with BOM)"
raw_small.srt        31 0A 30 ...  无 BOM   ← seconv 却报 "utf-8 (with BOM)"
snapped_small.srt    31 0A 30 ...  无 BOM   ← seconv 却报 "utf-8 (with BOM)"
test_B_utf8bom.srt   EF BB BF ...  有 BOM   ← 唯一真带 BOM 的
```

**seconv 5.2.0 对全部 UTF-8 文件都报 "with BOM"。因此编码/BOM 验证必须用 `scripts/check_srt.py`（字节级判定），不能用 seconv。**

| 11 | Whisper 解码参数 | `vad_filter=True`、`word_timestamps=True`、`condition_on_previous_text=False`、`no_speech_threshold=0.6`、`compression_ratio_threshold=2.4` | 抑制幻觉循环与静音段重复 | 高 |

### 尚未解决、需在正式开发中补齐的一环

**Whisper 会把多个语句合并进一段**：本素材波形上有 **123 个语句**，而 Whisper 只输出 **54 段**（large-v3 为 63 段）。其中 5 条修正量 ≥1s，正是"一段跨多句"造成的。

**因此第四板块的校正流水线必须是：**
```
1. 提取音频（16kHz 单声道）
2. faster-whisper 转写（参数见 #11）
3. 剔除无效段（空文本/纯空白/零时长/幻觉重复）
4. 【缺失，必须实现】按静音边界切分合并段   ← 用 silencedetect 的静音区间，
     把跨越多句的 Whisper 段切开，每句独立成条
5. 波形吸附（本模块，参数见 #9）
6. 行长/行数约束（#3 #4）
7. seconv 微调（可选：--offset / --adjust-duration / FixCommonErrors）
8. 强制 UTF-8 无 BOM + 结构校验（check_srt.py，必须零 ERROR）
9. 输出 srt + remux mp4
```

| `snap_to_waveform.py` | **波形吸附**（已验证算法）：把字幕时间戳吸附到真实语音边界，自带输出自检。 |
| `measure_whisper_drift.py` | **偏差测量**：量化 Whisper 时间戳系统性偏差，可输出原始 SRT。 |

| `fetch_file.py` | **带断点续传与重试的下载器**（解决 GitHub 直连中断）。 |

### 内容保真检查：守住最危险的一类 bug

字幕校正最大的风险**不是报错，而是静默地把音频和文本对错位**——时间戳全部合法、格式完全正确、`seconv lint` 也通过，但听感上字幕和语音对不上。

`check_srt.py --baseline <原始.srt>` 专门守这个门：比对校正前后的**段落数量、文本内容、段落顺序、文本相似度、总跨度**。顺序被调换会直接报 ERROR（"音频与文本错位的典型信号"）。

实测确认：本次吸附过程**文本序列完全一致**（54→54 条，逐条相同），即算法只动时间戳、不碰内容。

### 无法自动化的一环

**Aboboo 没有命令行接口**（已扫描 `aboboo.exe`：无 `/silent`、`--`、`import` 等参数，仅含 `UIAutomationCore.dll` GUI 无障碍层）。因此第五节表格必须人工完成。

### 探针素材（`test_output\probe\`）

8 个 SRT 变体、2 个测试 MP4、`raw_small.srt`（原始 Whisper 输出）、`snapped_small.srt`（吸附后）、`drift_*.json`（偏差数据）、`snap_report.json`（吸附报告）。

### 工程化文件

| 文件 | 作用 |
|---|---|
| `config/subtitle_params.json` | **硬参数的机器可读形式**。`check_srt.py` 启动时读取它并覆盖内置阈值，这样上表的参数是**真正可执行**的，而不是停在文档里。改这个文件即可调整门禁严格度。 |
| `requirements.txt` | 实测可用的版本清单 + 国内镜像与 pip 缓存重定向说明 |
| `.gitignore` | 排除 3GB 模型缓存、132MB seconv、84MB pip 缓存等不可提交内容 |

**实测验证**：把 `单行最大字符数` 从 43 改为 200 后，154 字符的超长行不再告警（告警数 1→0），确认阈值确实由配置驱动。

**已知坑**：配置文件**不能带 BOM**（`config/subtitle_params.json` 若被记事本存成带 BOM 的 UTF-8，会触发 `JSONDecodeError`）。此时校验器会**静默回退内置默认值且不崩溃**——已在代码中做兜底，但团队改参数时请用 UTF-8 无 BOM 保存。
