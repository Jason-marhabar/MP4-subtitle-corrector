# 第二板块模块说明（业务调度与多线程控制）

> 面向第一板块（GUI）与第五板块（测试）。
> 第四板块（ASR + 字幕校正）见 [第四板块-模块说明.md](第四板块-模块说明.md)。

## 分层设计

```
controller/
├── scheduler.py    调度核心（纯标准库，不依赖 Qt）
└── qt_worker.py    Qt 适配层（可选导入）
```

**为什么核心不依赖 Qt** —— 这个分层是有意为之：

| 理由 | 受益方 |
|---|---|
| 少一层 Qt 耦合，PyInstaller 打包更省事 | 第六板块 |
| 并发/批量/取消逻辑可在无 GUI 环境测试 | 第五板块 |
| 换 GUI 框架或改接口时调度核心不用重写 | 第一板块 |

已验证：导入 `controller.scheduler` 后加载的 Qt 模块数为 **0**；
未安装 PySide6 时 `import controller.qt_worker` **不报错**，只是
`available()` 返回 False，构造 `SchedulerWorker` 才给出安装指引。

## 核心概念

### Job 状态机

```
WAITING ──> RUNNING ──> DONE
   │           │    └──> FAILED      （异常，已捕获并记录文本）
   │           └──────> CANCELLED   （取消传播）
   └──────────────────> CANCELLED   （排队中被直接标记）
   └──────────────────> SKIPPED     （文件不存在 / 未指定输出目录 / 输出已存在）
```

`SKIPPED` 与 `FAILED` 分开是有意的：前者是**预期内的跳过**（用户可自行处理），
后者是**意外错误**（需要排查）。GUI 可以据此用不同颜色区分。

### 线程模型

```
GUI 线程 ──add_files()/start()──> 队列 ──> 工作线程池(N 个)
   ↑                                            │
   └────────── 回调（在工作线程触发）────────────┘
```

> ⚠️ **所有回调都在工作线程中被调用。** 回调里若直接改 Qt 控件会崩。
> 用 `qt_worker.SchedulerWorker` 时，它的回调是 `Signal.emit`，
> Qt 会以 QueuedConnection 投递到 GUI 线程执行，天然安全。

## 对外接口

### 纯逻辑用法（脚本 / 测试 / 无 GUI）

```python
from controller.scheduler import BatchScheduler, BatchConfig

cfg = BatchConfig(out_dir="D:/out", workers=2, model="small",
                  device="cpu", compute_type="int8")
sched = BatchScheduler(cfg)
sched.on_job_update = lambda job: print(job.name, job.state.value, job.progress)
sched.on_progress   = lambda p: print(p.text(), f"{p.overall:.0%}")
sched.on_log        = lambda lvl, msg: print(f"[{lvl}] {msg}")
sched.attach_logging()          # 把 model/controller 的 logging 接到 on_log

problems = validate_batch_inputs(files)   # 导入前校验，返回问题列表
sched.add_files(files)
jobs = sched.run(block=True)              # 阻塞；block=False 则立即返回
sched.shutdown()
```

### GUI 用法（PySide6）

```python
from controller.qt_worker import SchedulerWorker
from controller.scheduler import BatchConfig, STATE_TEXT

self.worker = SchedulerWorker(BatchConfig(out_dir=self.out_dir, workers=2))
self.worker.jobUpdated.connect(self.on_job_updated)        # 更新任务列表行
self.worker.progressChanged.connect(self.on_progress)      # 更新总进度条
self.worker.logMessage.connect(self.append_log)            # 追加日志
self.worker.batchFinished.connect(self.on_batch_finished)  # 恢复按钮状态
self.worker.failed.connect(self.on_batch_failed)           # 批次级异常

self.worker.add_files(paths, out_dir=self.out_dir)
self.worker.start()          # 非阻塞，界面不卡
# 取消：self.worker.cancel_all() / self.worker.cancel_job(job_id)
```

`JobRow.from_job(job).as_row()` 直接给出表格一行（文件名/状态/进度/说明），
`JobRow.COLUMNS` 是列标题 —— 列定义由调度层提供，避免 GUI 与调度对字段名产生分歧。

## 关键行为（均已测试验证）

| 行为 | 说明 | 测试用例 |
|---|---|---|
| **模型只加载一次** | `AsrEngine` 由调度器持有并复用。CPU 上 large-v3 单次加载实测 281s，批量 10 个文件若各自加载会白等数十分钟 | 用例 2（`load_count == 1`） |
| **单任务失败不中断队列** | 统一异常捕获，失败任务记录错误文本，其余照常处理 | 用例 3 |
| **取消可传播** | 排队中立即标记；运行中通过 `cancel_flag` 传播，实测 6s 的任务 0.6s 内中止 | 用例 4、5 |
| **已取消任务不产出残件** | 第四板块在取消时会清理半成品 SRT | 用例 4 |
| **进度单调不回退** | 多线程上报经 `_notify_lock` 串行化，避免交错 | 用例 2（27 次上报全程单调） |
| **不覆盖用户成果** | 输出已存在且未开 `overwrite` 时跳过，而非静默覆盖 | 用例 7 |
| **配置损坏不崩** | `BatchConfig.from_json` 读失败时回退默认值并告警，忽略未知字段 | 用例 8 |
| **导入前校验** | 空文件 / 非视频扩展名 / 重复导入 / 文件不存在 / 无法读取时长 | 用例 1 |

## 验证方式

```bat
:: 调度逻辑（假任务注入，秒级完成，覆盖并发/取消/失败隔离）
venv\Scripts\python.exe scripts\test_scheduler.py

:: 额外跑一次真实素材端到端（约 30s，经调度层完整走一遍）
venv\Scripts\python.exe scripts\test_scheduler.py --real
```

**为什么用假任务注入**：调度层要验证的是并发、排队、取消、失败隔离、进度聚合
这些**逻辑正确性**，与"转写是否准确"无关。假任务能在几秒内精确构造边界场景
（失败、卡住、取消、慢任务），而真实转写一次要 40 秒且难以制造这些情况。

实测结果：**34/34 通过**；真实端到端产出 **99 条字幕、耗时 27.6s**，
与直接调用管线一致。

### 测试中发现并修正的自测脚本缺陷

假实现会在用例之间**泄漏**：`case_real` 起初跑的是前面注入的假任务，
产出 `cue_count=7`、耗时 0.1s 的假结果并被断言接受（误报）。
→ 修正：真实用例前调用 `restore_real_modules()` 重新加载模块。

## 给第一板块的接入建议

1. **导入即校验**：文件选择后先调 `validate_batch_inputs()` 与
   `has_audio_stream()`，把问题在排队前反馈，不要等处理到一半才报错。
2. **不要自己起线程**：直接用 `SchedulerWorker`，避免和调度层的线程池叠加。
3. **进度条用 `overall`**：它是按任务加权的总进度（运行中任务按自身进度计入），
   比"已完成任务数/总数"更平滑。
4. **关闭窗口时调 `shutdown()`**：会取消所有任务并释放模型资源。
5. **并发数建议**：`workers=1` 最稳（GPU 显存、CPU 都只有一个）；
   若用 GPU 且显存充裕可设 2，但同一模型实例并发推理需自行确认显存是否够。
